# ERP V1 · 技术服务全流程

关联总控：[#8](https://github.com/nekox41/zjerp/issues/8)

## 业务主链路

```text
客户 / 合作方
    └─ 合同（直接签约或合作方介绍、分成比例）
         └─ 项目（可先于合同创建；合同与项目多对多）
              └─ 服务工作包
                   ├─ 多次现场服务（日期、类型、现场执行人员）
                   │    └─ 问题清单（发现、整改、复核、关闭）
                   ├─ 照片批次（原始照片、一级系统分类、拍摄日期、人工确认、排序）
                   │    └─ 独立工程师审核
                   └─ 报告
                        ├─ DOCX 模板 + 对应系统照片表格插图
                        ├─ 报告版本与生成文件历史
                        ├─ 内部工程师审核 / 退回 / 修订
                        ├─ 独立签发
                        └─ 邮寄 / 现场 / 电子交付登记与状态历史
```

维护保养项目另有合同续签历史、小蜜蜂状态、项目资料、公示卡和按需维护日期/现场人员登记。

## 技术服务前端操作

1. 在「业务管理」创建客户、员工、合同和项目。合同服务类型选择维护保养、消防检测、消防评定、消防评估或其他技术服务。
2. 在「合作方与维保」维护中间人/合作方，关联合同和约定分成；将合同关联一个或多个项目。
3. 项目负责人和技术负责人通过项目人员页分配。两者必须是不同的在职工程师，且都有有效资格记录；服务端会再次校验。
4. 在「技术服务交付」选择项目和工作包，登记每次到场日期、类型、人员和现场情况。问题清单可以分配责任人、记录整改结果，并关联到某次到场。
5. 为每次现场采集建立照片批次，批量导入 JPG/PNG。照片原文件保留；每张照片必须由工作人员选择一级消防系统、填写拍摄日期并勾选人工核对。支持卡片/表格、修改、排序和筛选。
6. 整理人提交批次后，由另一名具有有效工程师资格的员工审核。
7. 创建报告草稿并填写 ERP 流程记录字段。上传当前报告 DOCX，选择已审核照片批次后生成新 DOCX。
8. 默认使用“追加”模式：在相应系统章节最后一个“现场检测照片”表格中追加照片行，保留模板现有照片。若明确需要用本批次替换模板中所有系统照片，可选择“替换”模式；该模式会移除未被本批次替换的模板照片。
9. 报告审核人必须与编制人不同；签发人必须与编制人和审核人都不同。签发后可以登记快递、现场或电子交付，更新寄出、签收或退回状态。
10. 每次生成的 DOCX 都按报告版本和生成修订号保存，旧文件不会覆盖。

## DOCX 模板约定与样本适配

- 当前支持两份已分析样本中的一级系统标题。消防应急照明标题兼容“消防应急照明和疏散指示系统”与“消防应急照明及疏散指示系统”。
- 在每个系统章节内识别“现场检测照片”段落及其后方的 Word 图片表格。样本主要为 2×2 网格，部分表格少于四张。
- 追加模式把新照片行放到该系统最后一个图片表格内；替换模式重用现有 2×2 网格，必要时扩展最后一个表格，并清除未使用的样本照片组。
- 用户分类的系统若在所选 DOCX 中不存在，生成会明确报错，不会把照片放到其他系统。
- 每张照片的拍摄日期作为照片格中的说明文字。系统不依赖水印或 EXIF；缺少信息时必须人工填写。
- 两份样本检测系统范围不同；例如自动喷水灭火和防烟排烟系统并非每个样本都有。必须选择与本次报告系统范围匹配的 DOCX。
- 模板正文、检测项目结果、系统判定、最终结论和签章仍由上传 DOCX 提供。本工作流不自动推断或改写检测结论/签章；ERP 摘要、范围、方法、发现和结论字段用于流程记录与审核，并不自动覆盖 DOCX 正文。

## 状态与安全规则

### 照片批次
`collecting → submitted → reviewed → locked`

- collecting：可新增/删除/修改照片。
- submitted：所有照片必须有分类、日期并标记人工确认。
- reviewed：另一名有效工程师审核通过。
- locked：已用于报告，不可再修改。

### 报告
沿用既有状态机：`draft → submitted → reviewing → approved → issued → archived`，退回和修订按既有规则处理。报告编制人与审核人、签发人相互分离。

### 交付
`prepared → dispatched → delivered`；允许 `dispatched → returned → dispatched`，准备阶段可取消。交付记录关联到具体报告版本，并要求该版本已经生成 DOCX。

### 文件与权限
- 文件保存在私有存储，数据库保存文件 ID、SHA-256、媒体类型和大小。
- 图片批次、报告 artifact、合同附件均通过业务关系授权读取。
- 新增表与权限只通过 Flyway V8/V9 迁移；旧版 `server` 数据库不参与。
- 不提供未经授权的公开文件 URL。

## 尚需完成的验收

- 在隔离 MySQL 上完整运行 V1–V9 migrations 与 schema smoke test。
- 后端 Maven 测试和前端生产构建通过。
- 使用两份真实 DOCX 分别生成“追加”和“替换”输出，在 Microsoft Word 中核对每个系统的图片数量、日期、表格分页和打印布局。
- 使用真实员工/权限账号走完：多次到场 → 问题整改 → 照片批次审核 → DOCX → 报告审核/退回/修订 → 签发 → 邮寄签收。
- 生产环境上传大小、私有文件读写和备份恢复测试。

CI 成功不代表 Word 版式和实际业务验收完成。
